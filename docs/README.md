# OctoAcme Project Management Docs

This repository centralizes the standard project management guidance used by OctoAcme. The documents below provide a practical operating model for initiating, planning, delivering, releasing, and improving work across cross-functional teams.

## Project management process summary

OctoAcme follows a lightweight, cross-functional project lifecycle designed to turn ideas into measurable outcomes with clear ownership and consistent communication:

- Initiation: validate the business need, identify stakeholders, define success metrics, and create a high-level project brief.
- Planning: align backlog priorities, milestones, dependencies, roles, and quality expectations before delivery begins.
- Execution: run work through daily coordination, progress tracking, risk management, and milestone reviews.
- Release & deployment: confirm readiness, deploy with checks, verify outcomes, and communicate release status to stakeholders.
- Retrospective & improvement: capture lessons learned, assign action items, and continuously improve the delivery process.

The project model emphasizes customer value, iterative delivery, clear ownership, and data-informed decisions. Team rhythms include daily standups, weekly delivery syncs, demos, and regular stakeholder communication so work stays visible and aligned with goals.

## Roles and responsibilities

OctoAcme uses a cross-functional role model to balance delivery and decision-making:

- Developers build, test, and maintain quality across the product.
- Product Managers define the problem, prioritize the roadmap, and measure success.
- Project Managers coordinate schedules, risks, dependencies, and communication.
- QA and testing partners validate quality and acceptance criteria.
- Stakeholders provide input, approvals, and business context.

These roles work together to keep scope, quality, and delivery expectations clear and consistent.

## Quality assurance and working practices

Quality is built into the project lifecycle rather than added at the end. OctoAcme expects teams to use acceptance criteria, test coverage, CI checks, security scanning, and smoke testing for critical workflows. Work is reviewed through project boards, PR standards, and definition-of-done checks before it is considered ready for release. Risks and blockers are managed actively, escalated through clear paths, and revisited in regular status or weekly review meetings.
